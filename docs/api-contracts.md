# API Contracts — Hexalith.Parties

> Regenerated by BMAD *Document Project* (**full rescan**, deep, 2026-06-02) and reconciled for Epic 8 closure on 2026-08-18. Sources: `src/Hexalith.Parties.Client/`, `src/Hexalith.Parties.Mcp/`, `src/Hexalith.Parties/` (host ingress). `parties-mcp` exposes **exactly 5 tools** (no `get_party_name_at`). For the end-to-end walkthrough with copy-paste curl/PowerShell, see **[getting-started.md](getting-started.md)**.

## The boundary in one picture

```
 .NET consumer ──► IPartiesCommandClient / IPartiesQueryClient ─┐
 AI assistant  ──► parties-mcp (5 tools) ──► typed client ──────┤
 Any HTTP client ──────────────────────────────────────────────┤
                                                                ▼
                                   Hexalith.EventStore gateway  (PUBLIC)
                                   POST /api/v1/commands   Domain="party"
                                   POST /api/v1/queries    Domain="party"
                                   (authn, tenant validation, RBAC, routing)
                                                                │ DAPR service invocation
                                                                ▼
                                   parties SDK domain-service host (INTERNAL only)
                                   /process · /query · /project* · /replay-state
                                   /admin/operational-index-metadata · /project/rebuild/*
```

**Key rule:** the `parties` domain-service host has **no public command/query
API**. All public traffic enters through the EventStore gateway. Its DAPR ACL is
deny-by-default and allows only the `eventstore` app ID to invoke the exact POST
SDK routes listed in §4. AI assistants connect to the **separate `parties-mcp`
host**, not to `/mcp` on `parties`.

## 1. Public HTTP gateway (EventStore)

Owned by **Hexalith.EventStore**, not by this repo, but Parties defines the command/query *shapes*. Base URL = the `eventstore` gateway (the `Parties:BaseUrl` config value), **not** the Parties domain-host URL.

### Commands — `POST /api/v1/commands`

Envelope (camelCase JSON):

| Field | Meaning |
|-------|---------|
| `messageId` | client-generated id (GUID "N") |
| `tenant` | tenant id (required) |
| `domain` | `"party"` |
| `aggregateId` | the `partyId` |
| `commandType` | fully-qualified .NET command type, e.g. `Hexalith.Parties.Contracts.Commands.CreateParty` |
| `payload` | the command object |
| `correlationId` | usually `= messageId` |

Response carries a `correlationId` (and optionally a `resultPayload` echoing the updated `PartyDetail`). **Acceptance is not read-your-write** — projections are eventually consistent.

**Command types accepted** (the `commandType` field): every command in [data-models.md §3](data-models.md) — `CreateParty`, `CreatePartyComposite`, `UpdatePartyComposite`, `UpdatePersonDetails`, `UpdateOrganizationDetails`, `SetIsNaturalPerson`, `AddContactChannel`, `UpdateContactChannel`, `RemoveContactChannel`, `AddIdentifier`, `RemoveIdentifier`, `DeactivateParty`, `ReactivateParty`, and the GDPR commands (`RecordConsent`, `RevokeConsent`, `RestrictProcessing`, `LiftRestriction`, `EraseParty`, `CancelPartyErasure`, `RetryErasureVerification`, …).

Contact-channel IDs must be unique ignoring case (`OrdinalIgnoreCase`). A
case-only duplicate addition rejects the standalone command or the entire
composite create/update with `CompositeOperationConflict`; exact-ID addition
retries retain their existing no-op/skip behavior. Channel updates, removals,
and consent lookups still address stored IDs exactly, including letter case.

Historical case-only channel pairs replay unchanged. Updates and consent grants
for an ambiguous channel family reject with a fixed conflict message; unrelated
channels remain usable. An exact channel removal can resolve that ambiguity.
Consent IDs retain the existing lowercased `channel:purpose` generation. Before
recording or treating a grant as an idempotent retry, the aggregate rejects a
generated ID already owned by a different exact channel, including revoked
records and removed channels. Removing a channel does not release its retained
consent IDs for another case variant. The collision guard permits the existing
exact-ID revocation behavior when ownership is unambiguous, even with ambiguous
current channels, but rejects an exact consent ID shared by different channel
owners. A pre-existing renewal limitation remains: grant → revoke → regrant can
leave the first revoked record selected by a later revoke, producing a no-op
while the later grant remains active. This requires separate lifecycle work.
These conflicts do not rewrite historical
events or consent records. Resolving cross-owner consent history requires a
separately designed remediation; channel removal alone does not resolve it.

Consent commands validate their payloads before protected state is rehydrated.
`RecordConsent.LawfulBasis` must be a defined value: `Consent`,
`LegitimateInterest`, `ContractualNecessity`, or `LegalObligation`.
`RevokeConsent.Reason` is optional and limited to 256 UTF-16 code units
(`string.Length`), including whitespace; validation does not trim the reason.
Null, empty, and whitespace reasons within that limit remain valid. An undefined
numeric lawful basis or an oversized reason produces the internal
`PartyCommandValidationRejected` event with the property name and a fixed
`EnumValidator` or `MaximumLengthValidator` code, respectively. An unknown enum
name fails JSON deserialization and produces the internal `Payload`/`InvalidJson`
diagnostic. These rejections emit no consent success event. The public gateway
returns HTTP 422 Problem Details with `reasonCode="party-command-validation-rejected"`
and `rejectionType`; it does not expose internal property names or validator codes.

Production `AddParties` registration supplies the command validators. If a
validator is missing, the processor rejects the command before protected-state
access with the internal `CommandType`/`ValidatorNotRegistered` diagnostic and
the same public validation-rejection response. The four legacy aggregate-only
commands (`MarkPartyEncryptionKeyDeleted`, `MarkErasureVerified`,
`CompletePartyErasure`, and `RotatePartyKey`) retain their existing behavior
without validators; a validator registered for any of them still runs.

### Queries — `POST /api/v1/queries`

Envelope fields: `tenant`, `domain="party"`, `aggregateId`, `queryType`, `entityId`, optional `payload`. The gateway maps `queryType` to the advertised Parties SDK `IDomainQueryHandler`.

| `queryType` | `aggregateId` | Payload | Returns |
|-------------|---------------|---------|---------|
| `PartyDetail` | the partyId | — | `PartyDetail` |
| `PartyIndex` | `"parties"` | `{ page, pageSize, type?, active?, created/modified after/before }` | `PagedResult<PartyIndexEntry>` |
| `PartySearch` | `"parties"` | `{ query, page, pageSize, mode? }` | `PagedResult<PartySearchResult>` |
| `ExportPartyData` | the partyId | `{ partyId }` | `PartyDataPortabilityPackage` |
| `GetProcessingRecords` | the partyId | `{ partyId }` | `ProcessingActivityRecord[]` |
| `GetErasureStatus` | the partyId | `{ partyId }` | `PartyErasureStatusRecord?` |
| `GetErasureCertificate` | the partyId | `{ partyId }` | `ErasureCertificate?` |

#### `PartySearch` wire-mode allowlist (fail-closed)

The `mode` payload field is a string. **Only** these values are honoured (everything else fails closed with `UnsupportedQueryType` *before* the projection read, echoing no tenant/query detail):

- omitted / `null` / empty → MVP display-name search
- `"Lexical"` → display-name lexical search
- `"DisplayName"` → alias of the same

Reserved future values (`"Hybrid"`, `"Semantic"`, `"Graph"`, `"Email"`, `"Identifier"`, `"TemporalName"`) are **rejected** in MVP. The in-process `PartySearchMode` enum is intentionally wider than this allowlist. See [deferred-search-and-temporal-queries.md](deferred-search-and-temporal-queries.md). When Memories-backed search is enabled, additional rich modes apply — see [memories-backed-party-search.md](memories-backed-party-search.md).

## 2. Typed .NET client — `Hexalith.Parties.Client`

`dotnet add package Hexalith.Parties.Client`, then `builder.Services.AddPartiesClient(builder.Configuration)`. Config section `Parties`:

```json
{ "Parties": { "BaseUrl": "https://<eventstore-gateway>", "Tenant": "tenant-a" } }
```

Registration (`Extensions/PartiesClientServiceCollectionExtensions.cs`) eagerly validates `BaseUrl` (absolute http/https) and `Tenant` (non-empty) — **throws at startup** if invalid — and registers three typed `HttpClient`s. The clients hide the EventStore envelope; **tenant travels in the envelope body**, not a header.

### `IPartiesCommandClient`

`src/Hexalith.Parties.Client/Abstractions/IPartiesCommandClient.cs` (impl `HttpPartiesCommandClient`). Every command has **two overloads**:

- `…Async(...) : Task<string>` — returns the **correlationId** ("fire").
- `…WithResultAsync(...) : Task<PartiesCommandResult<PartyDetail>>` — correlationId + optionally-enriched `PartyDetail`.

| Method (Async / WithResultAsync) | Parameters |
|----------------------------------|-----------|
| `CreatePartyAsync` | `CreateParty, ct` |
| `CreatePartyCompositeAsync` | `CreatePartyComposite, ct` |
| `UpdatePartyCompositeAsync` | `string partyId, UpdatePartyComposite, ct` |
| `UpdatePersonDetailsAsync` | `string partyId, UpdatePersonDetails, ct` |
| `UpdateOrganizationDetailsAsync` | `string partyId, UpdateOrganizationDetails, ct` |
| `SetIsNaturalPersonAsync` | `string partyId, SetIsNaturalPerson, ct` |
| `AddContactChannelAsync` | `string partyId, AddContactChannel, ct` |
| `UpdateContactChannelAsync` | `string partyId, UpdateContactChannel, ct` |
| `RemoveContactChannelAsync` | `string partyId, RemoveContactChannel, ct` |
| `AddIdentifierAsync` | `string partyId, AddIdentifier, ct` |
| `RemoveIdentifierAsync` | `string partyId, RemoveIdentifier, ct` |
| `DeactivatePartyAsync` | `string partyId, ct` |
| `ReactivatePartyAsync` | `string partyId, ct` |

`PartiesCommandResult<TPayload>` = `record (string CorrelationId, TPayload? Payload)`. For `partyId`-taking overloads the client re-stamps `command with { PartyId = partyId }` so the route id is authoritative. Result enrichment is best-effort and **fails closed** — you only get a `PartyDetail` when the gateway echoes a matching-id `resultPayload`.

### `IPartiesQueryClient`

`src/Hexalith.Parties.Client/Abstractions/IPartiesQueryClient.cs` (impl `HttpPartiesQueryClient`).

| Method | Returns | Notes |
|--------|---------|-------|
| `GetPartyAsync(string partyId, ct, requestCustomizer?)` | `PartyDetail` | party-detail projection |
| `ListPartiesAsync(page, pageSize, PartyType? type, bool? active, createdAfter?, createdBefore?, modifiedAfter?, modifiedBefore?, ct)` | `PagedResult<PartyIndexEntry>` | filtered list |
| `SearchPartiesAsync(string query, page, pageSize, ct, string? mode = null, string? caseId = null, requestCustomizer?, PartyType? type = null, bool? active = null)` | `PagedResult<PartySearchResult>` | display-name search with optional type/active filters |

`requestCustomizer: Func<HttpRequestMessage, CancellationToken, ValueTask>` lets direct consumers add auth/tenant headers before send.

AdminPortal uses the optional `type` and `active` parameters to keep debounced display-name search, Person/Organization filtering, active filtering, and server paging in one EventStore query instead of filtering a returned page in the browser.

> **No temporal "name-at" query exists.** Temporal name data is only the `NameHistory` list inside `PartyDetail`; there is no as-of resolution method (reserved — see [deferred-search-and-temporal-queries.md](deferred-search-and-temporal-queries.md)).

### `IAdminPortalGdprClient`

`src/Hexalith.Parties.Client/AdminPortal/IAdminPortalGdprClient.cs` — a GDPR-focused client over the same gateway, used by the AdminPortal and by the `parties-ui` self-scoped Consumer adapters. Methods: `RequestErasureAsync` (→ `EraseParty`), `CancelErasureAsync` (→ additive `CancelPartyErasure`), `GetErasureStatusAsync` (→ `GetErasureStatus` via `PartyDetailProjectionQueryActor` and authoritative erasure status), `RestrictProcessingAsync`/`LiftRestrictionAsync`, `AddConsentAsync` (→ `RecordConsent`) / `RevokeConsentAsync`, `GetConsentAsync`, `ExportPartyDataAsync` (→ `ExportPartyData` → JSON download), `GetProcessingRecordsAsync` (→ `GetProcessingRecords`), `GetErasureCertificateAsync` (→ `GetErasureCertificate`), and `RetryErasureVerificationAsync` (→ `RetryErasureVerification`). Results map to an `AdminPortalGdprOutcome` enum (Accepted/Completed/ValidationRejected/Forbidden/ContractUnavailable/…).

The erasure certificate path uses the existing `PartyDetailProjectionQueryActor` query route; it does not add a public `parties` endpoint or a DAPR `/query` service-invocation allowance. `RetryErasureVerification` is an EventStore command that the Parties domain service handles through the existing erasure orchestrator and record store.

### Transport details

- Commands serialise to a private `EventStoreCommandRequest` record (`messageId`, `tenant`, `domain="party"`, `aggregateId`, `commandType = typeof(T).FullName`, `payload`, `correlationId`) → `POST api/v1/commands`.
- Queries serialise to `Hexalith.EventStore.Contracts.Queries.SubmitQueryRequest` (tenant, domain, aggregateId, queryType, projectionType `party-detail`/`party-index`, payload, entityId, projectionActorType) → `POST api/v1/queries`.
- **JSON options:** camelCase, ignore-null, `JsonStringEnumConverter`.
- **Correlation:** client-generated `messageId = Guid("N")`, used as both `MessageId` and `CorrelationId`. No explicit idempotency header.
- **Errors:** RFC 9457 `problem+json` parsed into `PartiesClientException(Status, Title, Type, Detail, CorrelationId)`; `Detail` is **redacted** when it matches sensitive tokens (payload/token/authorization/bearer/secret/password/dapr/redis/connection string/api-key).

## 3. MCP host — `parties-mcp`

`src/Hexalith.Parties.Mcp/`. A **separate** ASP.NET host (no DAPR sidecar) exposing Model Context Protocol tools over Streamable HTTP (`app.MapMcp()`, stateless). It forwards `Authorization`, `X-Tenant-Id`, `X-User-Id` from the request to the EventStore gateway via the typed client (`McpContextForwardingHandler`); it does **not** call the Parties domain-service host directly.

Client config:

```json
{ "mcpServers": { "hexalith-parties": {
  "url": "https://<parties-mcp>/mcp",
  "headers": { "Authorization": "Bearer <token>", "X-Tenant-Id": "tenant-a", "X-User-Id": "<user-id>" }
}}}
```

### Tools (exactly 5)

`Tools/PartiesMcpTools.cs` ([`McpServerToolType`]). Tool names in `Tools/PartiesMcpToolNames.cs`.

| Tool | Annotations | Behaviour |
|------|-------------|-----------|
| `get_party` | ReadOnly | `GetPartyAsync(partyId)`; returns `not_found` if the party is erased. |
| `find_parties` | ReadOnly | Display-name search (when `query` non-empty) or filtered list; params `query?, page, pageSize, type?, active?, created/modified after/before`. Clamps page≥1, pageSize 1–100. |
| `create_party` | Destructive | Forgiving AI-friendly input (`givenName`/`familyName` + aliases, `legalName`, `email`, `phone`, `vatNumber`/identifier, …). Generates a safe `partyId` if absent, builds a `CreatePartyComposite`, enforces payload-size limits. |
| `update_party` | Destructive | Patch semantics; route `partyId` authoritative. Merges via a read, builds `UpdatePartyComposite`; `active` applied as a separate (Re)activate command. |
| `delete_party` | Destructive, Idempotent | **Soft deactivation** (MVP delete intent) — explicitly *not* GDPR erasure. Idempotent when already inactive. |

> ⚠️ **`get_party_name_at` does NOT exist.** It is not implemented (temporal name resolution is deferred); the actual tool set is the five above. (The README + getting-started previously listed it as a "canonical tool" — corrected 2026-06-02.) Treat any reference to `get_party_name_at` as out-of-MVP.

Tool results use a `PartiesMcpToolResult` envelope (`status`, `category`, `code`, `message`, `toolName`, `correlationId?`, `data?`). `PartiesClientException` status codes map to categories (400/422 `validation_failed`, 401 `unauthorized`, 403 `forbidden`, 404/410 `not_found`, 409 `conflict`, 408 `timeout`, ≥500 `downstream_failed`). Every tool requires tenant+user context, else `missing_context`.

The MCP host binds `Parties:Mcp` options (`EventStoreGatewayBaseUrl`, default `http://eventstore`). It registers the typed clients as per-request transients whose tenant comes from the request context.

## 5. Authentication, tenancy & RBAC

EventStore owns **public** authentication, tenant validation, and RBAC at the gateway. The `parties` host additionally enforces defense-in-depth JWT bearer auth (`Authentication:JwtBearer`) and keeps a **local tenant-access projection** (`ITenantAccessService`, projection-side only — never on the gateway request path). Role→permission mapping (from Hexalith.Tenants events):

| Tenants role | Read | Write | Admin |
|--------------|------|-------|-------|
| `TenantReader` | ✓ | | |
| `TenantContributor` | ✓ | ✓ | |
| `TenantOwner` | ✓ | ✓ | ✓ |

The tenant-access projection **fails closed** (missing tenant/user, unknown/disabled tenant, non-member, insufficient role → deny) and is eventually consistent. Full details: [tenant-access-projection.md](tenant-access-projection.md). HTTP status meanings — `401` missing/invalid token; `403` gateway tenant/RBAC rejection (before domain execution).

## 6. Eventual consistency & freshness

Queries read **projection state**, not the write path. A query immediately after a command may miss the new party or return freshness metadata (`Rebuilding`/`Stale`/`Degraded`). Retry with bounded backoff, prefer `PartyDetail` by id for first-round-trip checks, and use the EventStore Admin UI for stream evidence. Responses may carry `X-Service-Degraded` / `X-Stale-Data-Age` (degraded reads) and `X-Parties-Search-Status` / `X-Parties-Search-Degraded-Reason` (Memories search). See [getting-started.md](getting-started.md#freshness-and-eventual-consistency).

Canonical read outages withhold cached active party detail and all nonempty or
unknown cached indexes, including list/search results. The Parties query result
is a bounded `ActorException` failure without payload or degraded metadata; this
also applies during an ordinary outage without known erasure. Unsafe candidates
are evicted. A cached erased detail can still return defensively redacted data
with its original timestamps and stale/degraded metadata. Cached absent detail
retains not-found semantics; only an established empty cached index can return an
empty stale/degraded page. Export and processing queries use the same detail
admission first. If only the processing slot is unavailable, retained cached
Article 30 records remain available, or an empty degraded record list is returned
when that cache is absent.

### Generic McpCli command declarations (local migration increment)

The Contracts assembly declares exactly `parties.create-party`,
`parties.update-party`, `parties.reactivate-party` and `parties.deactivate-party`.
The module uses String identifiers, domain `party`, the existing full CLR command
wire names, and root `PartyId` for aggregate routing. Tenant authority remains in
the gateway envelope. `Hexalith.McpCli.Abstractions` 1.0.0 supplies declaration
attributes only; the package/source pair follows `UseHexalithProjectReferences`.
This increment does not enroll or publish a module or retire the legacy host.

McpCli payloads use exact CLR property casing and typed nested values. For example,
`parties.create-party` accepts:

```json
{"PartyId":"party-49","Type":"Person","PersonDetails":{"FirstName":"Ada","LastName":"Lovelace"},"ContactChannels":[{"PartyId":"party-49","ContactChannelId":"email-49","Type":"Email","Value":"ada@example.test","IsPreferred":true}]}
```

Supply IDs explicitly; every child `PartyId` must equal the root. No alias mapping,
ID generation, person/organization inference or read/merge patch is performed.
McpCli PartyId values use ASCII letters or digits plus `.`, `_` or `-`, start
and end with an ASCII letter or digit, and contain at most 128 characters.
McpCli refuses legacy braced, parenthesized and X-format GUID PartyId values
before Gateway submission, although Parties accepts them. Preserving those
legacy IDs or approving a conversion remains a C07 retirement gate.
An update supplies complete `PersonDetails` or `OrganizationDetails` replacements
and/or typed add, update or removal lists. A `PartyId`-only update is rejected;
every `UpdateContactChannels` item must supply at least one of `Type`, `Value` or
`IsPreferred` (including `false`). Activation is a separate command. Repeated
soft deactivation is a safe no-op after lifecycle guards and never performs GDPR
erasure.

Both shared composite validators enforce a maximum **raw UTF-16 length of 512
per string and 4096 combined**, without trimming or rewriting values. Every root,
nested, child and removal string occurrence counts, including whitespace and
repeated IDs. The tighter support-safe 128-character rule applies to `PartyId`,
`ContactChannelId`, `IdentifierId` and removal ID entries. Business identifier
`Value` strings retain the 512 UTF-16-unit limit. This is stricter than legacy wrapper counting of trimmed fields; the total
budget can bind before the configured composite sub-operation cap (default 100).
Explicit null lists and null list items reject; omitted lists retain empty defaults.
Create counts 1 plus every item in `ContactChannels` and `Identifiers` toward
the operation cap. Update counts each non-null details object plus every item
in its five operation lists. Removing a channel ID also listed for addition or
update rejects the entire update; adding and removing the same identifier ID
also rejects. An existing channel ID listed for both addition and update has
its addition skipped and its update applied.
All these checks run before protected aggregate state is accessed.

The four local vectors in `tests/conformance-vectors/mcpcli-v1/` target only the
unpublished scratch package `Hexalith.Parties.Contracts` **0.0.0-story49**. They
include prerequisite writes, repeat deactivation and semantic `parties.get-party`
postconditions using the approved `PartyDetail` / `party-detail` /
`PartyDetailProjectionQueryActor` route. Those Query contracts do not exist in this
increment: postconditions remain unexecuted until Story 4.10, which must rebind
vectors to the complete immutable artifact. Shared-validator format and artifact
checks do not prove handler effects. Stories 4.11/4.13 own parity and persistent
semantic proof. Maintainer approval must name the exact artifact hash and shared
validator revision. C06 error privacy, C07 legacy-ID reachability and C08 credential
and cross-tenant authorization evidence remain replacement/retirement gates.

The detail kind on update must match the existing party type; an update cannot
change that type. Omitted/null details preserve the existing object, while a
supplied object replaces it completely. Create requires the detail kind matching
`Type`, but also accepts/stores an extra opposite-kind object without changing
`Type`. Business identifiers are added or removed; there is no identifier-update
list. Contact updates require at least one non-null mutable member: omitted/null
preserves that member, `IsPreferred: false` clears that channel's preference,
and `Value: ""` replaces the value with an empty string. All contact kinds,
including PostalAddress/SocialMedia, store a raw string; no structured format is
defined. Preference is scoped to channel type; supply `IsPreferred: true` with a
type change to reconcile preferences in the target type.

`OrganizationDetails.IsNaturalPerson` defaults to false and initializes party
classification on create. Existing detail replacement changes the nested flag
without updating the established party classification; these four operations do
not provide a classification-change command. Lifecycle operations require an
existing unrestricted party with current erasure status Active, including
when requesting an already-current active state.

### Generic McpCli read declarations (local candidate)

The Contracts candidate declares exactly seven operations: `parties.get-party`,
`parties.list-parties`, `parties.search-parties`, `parties.create-party`,
`parties.update-party`, `parties.reactivate-party` and `parties.deactivate-party`.
The complete candidate still requires fresh maintainer approval, exact-source CI,
and the protected owning release workflow before its published version can be
pinned in Builds and enrolled in McpCli. The existing five-tool MCP host remains
available; this declaration work does not authorize retirement.

Queries use domain `party` and envelope tenant authority. Detail uses wire type
`PartyDetail`, projection `party-detail`, historical compatibility name
`PartyDetailProjectionQueryActor`, and root `PartyId`. List and search use wire
`PartyIndex` / `PartySearch`, projection `party-index`, compatibility name
`PartyIndexProjectionQueryActor`, and aggregate `parties`. The current SDK
`PartyDetailQueryHandler`, `PartyIndexQueryHandler` and `PartySearchQueryHandler`
dispatch directly to canonical read models; actor compatibility fields do not
prove actor execution. Omitted EntityId falls back to AggregateId; supplied
EntityId must match before any read. String IDs retain existing Parties syntax;
McpCli still refuses legacy braced, parenthesized and X-format GUID IDs.

Erased detail has the same safe not-found outcome as missing detail. Inactive
detail stays visible. List accepts optional `Type` (Person or Organization),
`Active`, and inclusive `CreatedAfter`, `CreatedBefore`, `ModifiedAfter` and
`ModifiedBefore` instants with explicit offsets. Invalid instants and inverted
ranges reject. Search accepts `Query`, `Type` and `Active`; it trims the query
and uses case-insensitive, diacritic-normalized display-name matching, including
fuzzy matches. Empty/whitespace query returns no matches. Date filters, CaseId,
unknown fields and unsupported search modes reject rather than being ignored;
legacy Lexical/DisplayName mode names remain accepted. Duplicate case aliases
such as `Type` plus `type` reject. Filters and erasure suppression apply before
paging and totals exclude erased entries.

The new Query DTOs have no payload paging members. When envelope Paging is
present, it alone governs: size defaults to 20, position to offset 0, maximum
size 100, and offsets must align with the effective size. A nonblank cursor
cannot combine with an offset. Cursors bind query type, tenant, user, filters
and size; changed scope rejects before reading. Response paging reports effective
size/offset, filtered total, hasMore and nextCursor. When envelope Paging is
absent, the legacy payload Page/PageSize behavior remains (page defaults to 1,
size to 20, maximum 100; nonpositive values reject).

`tests/conformance-vectors/mcpcli-v1/` contains seven vectors bound to the local
`0.0.0-story410` artifact, with prerequisite creates and original write-vector
Query postconditions retained. Shared McpCli validation and both-head replay
check wire envelopes, filtered totals, paging and result assertions. Scripted
replay does not prove live authorization, persisted domain effects or C06–C08;
Stories 4.11/4.13 remain required before replacement or retirement.
