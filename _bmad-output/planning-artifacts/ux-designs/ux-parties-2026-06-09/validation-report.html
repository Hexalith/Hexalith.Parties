Parties UI — UX Design Validation Report

_bmad-output/planning-artifacts/ux-designs/ux-parties-2026-06-09 · DESIGN.md + EXPERIENCE.md (final 2026-06-09) · re-validated 2026-08-18

A clean, genuinely source-extractable delta-spine pair: canonical shape on both files, committed tokens with load-bearing contrast caveats spelled out, a State Patterns section that actually carries the product's hardest problem (eventual consistency), and all five mocks linked with spine-wins stated. The one structural risk is source drift: the sources file (project-context.md) was revised 2026-06-21 — twelve days after finalize — and now carries consumer-binding (/no-party-binding) and Art. 18 restriction rules the spine pair does not reflect.

The three extra lenses shift the picture from "polish" to "reconcile." The behavioral spine is implemented with high fidelity — status-kind vocabulary, the polite/assertive live-region split, consent role=switch + default-Off + lawful-basis honesty, and the regulated erasure/export microcopy are in code near-verbatim and test-pinned; the picker's FAST→Fluent 2 re-skin debt is resolved in code and its spine debt annotations can be retired. But DESIGN.md's token layer drifts materially in the build: both portals style domain states against the banned legacy FAST --*-rest tokens (one selected-row outline silently vanishes), the per-area density contract was never wired, consumer surfaces /me/privacy and /me/edit are unreachable by navigation, and the consumer erasure confirm is a fake modal (aria-modal without trap/restore).

All 18 June finalize resolutions (6 accessibility + 12 regulated-language) verifiably landed in the spine text — no criticals anywhere this round. The remaining exposure is under-specified rights: the Object (Art. 21) button promises a right the backend has no command for (flagged independently by two lenses; it ships today as a permanently disabled control), restriction (Art. 18) is invisible to the data subject, the sign-in surface lacks a WCAG 2.2 §3.3.8 Accessible Authentication mandate, and the sign-in mock still paints link text in the raw 3.51:1 accent. Totals: 0 critical · 7 high · 22 medium · 24 low.

Regulated language review (GDPR)

review-regulated-language.md

Every June regulated-language resolution genuinely landed in the spine text and the mocks (12/12 verified) — and the copy is remarkably backend-aligned: the CancelPartyErasure guard's own rejection message is the spine's cancel-window sentence in the imperative. The remaining exposure has shifted from dishonest promises to under-specified rights: the Object affordance references a right the backend has no command for, restriction is invisible to the data subject, and two erasure-time edge behaviors are unspecced.

high

"Object to this use" (Art. 21) promises a right the backend does not deliver

EXPERIENCE §Voice and Tone, §Component Patterns, Flow 1 · Contracts/Commands
No Object/objection command, event, or workflow exists (24 commands verified, none Art. 21); no client method exists. The copy also implies pressing it stops the use, but Art. 21(1) objection can be refused on compelling-legitimate-grounds — the outcome is an assessment, not a toggle. Ships today as a permanently disabled button.
Fix: Either spec Object as a request-raising flow with honest review copy + add the backend command/DPO queue, or replace the button with a plainly-worded contact path and mark the spine row blocked-on-backend.
medium

Consent behavior during erasure is unspecced; the generic retry copy would be dishonest there

EXPERIENCE §State Patterns, Flow 2
The backend rejects consent commands during erasure; Flow 2's failure copy ("please try again") invites a retry that can never succeed. The mock sidesteps it by omitting the consent card — a choice the spine never ratifies.
Fix: In the erasure-in-progress row: consent toggles disabled with "Consent changes are paused while your data is being deleted"; surface the erasure-specific rejection reason, never the generic retry line.
medium

Restriction (Art. 18) is invisible to the data subject

EXPERIENCE §IA, §State Patterns
Admin-only fulfillment is defensible; total invisibility is not (Art. 12 transparency, Art. 18(3) notice). The subtle guard — consent edits stay allowed while restricted — is unspecced, so a developer could "helpfully" disable the toggles and break it.
Fix: Consumer-facing restricted treatment ("…you can still change your consent choices"), a request path on the privacy surface, and a Component Patterns pin that consent toggles remain enabled while restricted.
