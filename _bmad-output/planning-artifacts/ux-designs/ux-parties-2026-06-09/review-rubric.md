## 4. State coverage — adequate

Walked all eleven IA surfaces against the 17 State Patterns rows. Coverage of the eventual-consistency core remains the pair's best work: cold load, `NoData` (admin + consumer), `DisplayNameOnly`, accepted-but-processing, stale/degraded reads, `Validation`, erasure (cancellable / permanent / paused-consent / late-cancel), Restricted, No party binding, Export, `TransientFailure`, `LoadFailure`, `SignInRequired`, `TenantUnavailable`, `AdminRequired`/`Forbidden`, `Gone`/`NotFound`. The gap is not missing rows but a semantic collision inside the freshness rows, plus three source-declared states with no treatment.

### Findings
- **high** The three-state freshness contract is internally inconsistent at the row level. DESIGN.md L196–202 defines `stale` = Warning + "as of HH:MM" and `degraded` = Info + "showing last known — **never Warning**"; EXPERIENCE.md Component Patterns L114 repeats that split. But State Patterns L129 "**Stale read** (`Degraded`)" binds the copy "Showing what we last knew — refreshing" (the *last-known* semantic) to `{components.freshness-indicator.stale}` (the *Warning* token), and Voice and Tone L99 labels that same copy "(stale read)". Meanwhile the `StatusKind.Degraded` enum value — the thing the code actually emits on a last-known-cache fallback — is mapped to the *stale* token, and no row maps freshness `degraded` except accepted-but-processing (L128, with entirely different copy). `.memlog.md` records that a code fix is queued to implement this contract; as written the implementer must guess which token colors a `Degraded` read. *Fix:* split L129 into two rows keyed to real signals — **Stale** (`X-Stale-Data-Age` / `ProjectionFreshnessMetadata` age known → `stale` Warning + "as of HH:MM") and **Degraded** (`StatusKind.Degraded` / `X-Service-Degraded`, last-known-cache fallback → `degraded` Info + "Showing what we last knew — refreshing"); re-label Voice and Tone L99 "(degraded read)".
- **medium** `FR-Shell` (PRD L66–76) declares two routing states absent from the spine: an authenticated principal holding **neither** role "sees a fail-closed no-area state", and a principal holding **both** roles lands in Admin (Admin policy checked first). Foundation L21–22/L38–39 and the IA/State tables cover only the three single-role cases and `/no-party-binding`. *Fix:* add a "No area" state row (copy + Help & contact path, no data) and one sentence in Foundation on dual-role precedence.
- **medium** Admin erasure **verification** has source-declared states — `IErasureVerificationService.VerifyErasureAsync` → `ErasureVerificationReport`, commands `MarkErasureVerified` / `RetryErasureVerification` (`project-context.md` L142–147) — and Flow 3's climax depends on the report, but State Patterns has no row for verification pending / verified / verification failed → Retry, and the GDPR operations surface has no treatment for "shred accepted, not yet verified". *Fix:* add an "Erasure verification" row (pending: Info + "Verifying deletion across records…"; verified: neutral "Verified — deletion confirmed"; failed: `role=alert` + Retry, never success-green).
- **low** `FR-Consumer-1` requires "an erased self renders a PII-free tombstone", and Flow 5 step 5 has Marc viewing the verified state "while his session still lets him see it", but the `Gone`/`NotFound` row L140 lists surfaces "Detail, picker" only — My profile / Edit my profile after completed erasure is unspecified. *Fix:* extend the row's surface column to "Detail, picker, Consumer profile" with the consumer copy.
- **low** Edit forms (admin Create/Edit, Edit my profile) opened over a stale or degraded read have no treatment: is Save allowed, warned, or blocked when the prefill is last-known? `FR-Consumer-2` requires "prefilled values match stored values". *Fix:* one clause in the Stale/Degraded rows or the Validation row: "edit forms prefilled from a non-fresh read show the freshness indicator inline and keep Save enabled; the command's own validation is authoritative."
