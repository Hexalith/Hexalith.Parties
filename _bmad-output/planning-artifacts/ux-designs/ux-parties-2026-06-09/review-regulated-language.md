## Findings

- **[high]** The "Object to this use" affordance (Art. 21) promises a right the backend does not deliver. EXPERIENCE.md §Voice and Tone (row 5), §Component Patterns "Consent control" ("with an **Object** action where applicable"), Key Flow 1 step 3, and `consumer-privacy.html` State A all offer Object on legitimate-interest items — but `Hexalith.Parties.Contracts/Commands/` contains no Object/objection command, event, or workflow (verified: 24 commands, none Art. 21), and no client method exists. A rendered button that either 404s or silently no-ops on a legal right is worse than not offering it. Additionally, the copy implies pressing it stops the use, but Art. 21(1) objection to a security-purposed legitimate interest can be refused on compelling-legitimate-grounds — the outcome is an *assessment*, not a toggle. *Fix:* either (a) spec Object as a request-raising flow with honest copy ("We'll review your objection and reply — this use continues while we review") and add the backend command/DPO queue before the consumer portal ships, or (b) until then, replace the button with a plainly-worded contact path ("You can object to this use — contact us"), and mark the spine row as blocked-on-backend so a developer can't ship the dead button verbatim.

- **[medium]** Consent behavior during erasure is unspecced, and the generic rejection copy would be dishonest there. The backend rejects consent commands while erasure is in progress (project-context "consent commands **do** reject while erasure is in progress"; the same `RejectIfErasureInProgress` cascade guards lifecycle commands in `PartyAggregate`). EXPERIENCE.md §State Patterns "Erasure requested / in progress" says nothing about the consent controls, and Key Flow 2's failure copy ("We couldn't change this — please try again") invites a retry that can never succeed during erasure. `consumer-privacy.html` State B sidesteps it by omitting the consent card entirely — a mock choice the spine never ratifies. *Fix:* add to the "Erasure requested / in progress" state row: consent toggles render disabled with "Consent changes are paused while your data is being deleted"; if a stale view lets one through, surface the erasure-specific rejection reason, never the generic retry line.

- **[medium]** Restriction (Art. 18) is invisible to the data subject. `RestrictProcessing`/`LiftRestriction` exist and the Admin GDPR surface offers Restrict (§Information Architecture, `admin-parties.html` GDPR panel; the `restricted` badge is specced in both spines) — but the Consumer area neither offers restriction nor names how to request it, and nothing specs what a *restricted* consumer sees on their own profile/privacy surfaces. Admin-only fulfillment is defensible; total invisibility is not: Art. 12 transparency expects the subject to know the right exists and Art. 18(3) requires informing them before a restriction is lifted. The subtle backend behavior — consent edits stay **allowed** while restricted (Art. 18(3)) — is also unspecced, so a developer could "helpfully" disable the toggles for a restricted party and break the deliberate guard. *Fix:* add a consumer-facing restricted treatment to §State Patterns (badge/banner: "Processing of your data is currently restricted — you can still change your consent choices"), name a request path on the privacy surface (even just "You can ask us to restrict processing — contact us"), and pin in §Component Patterns that consent toggles remain enabled while restricted.

- **[medium]** The erasure confirmation promise has no specced delivery channel or artifact. §Voice and Tone and `consumer-privacy.html` State B promise "We'll confirm when it's done" — to a person whose contact data is being crypto-shredded and whose `party_id` claim binding (the consumer sign-in path) points at a party that will cease to resolve. The backend produces an `ErasureCertificate` and a consumer `GetMyErasureStatusAsync` exists, but the spine never says what the consumer-facing confirmation *is* (in-app status while still signed in? a PII-free reference number captured before shred?) or what the certificate means to them. Priya gets Flow 3's verification-report climax; Marc gets an unbacked promise. *Fix:* spec the confirmation mechanics in Key Flow 1's erasure counterpart or the State Patterns row: show a PII-free request reference at request time ("keep this number"), state that the status page confirms completion while the session lasts, and word the completed state as verified deletion ("We've deleted your data and verified it's gone") without exposing certificate internals.

- **[low]** Consent Off-state sub-label in the mock drifts into loss-framing. `consumer-privacy.html` State A: "Marketing emails — Off — no offers unless you turn this on" teases the benefit ("offers") of opting in, where the spine's own Flow 2 formulation is neutral ("Off — you won't get marketing emails"). Mild, but it's exactly the regulated microcopy a developer ships verbatim, and the spine's anti-pattern section bans asymmetric nudges. *Fix:* align the mock with the spine's neutral wording for every Off sub-label.

- **[low]** "erase" leaks into consumer copy against the plain-verbs rule. `consumer-profile.html` view-state note: "ask us to export or erase it" — §Voice and Tone (row 3) designates "Delete my data" as the consumer verb, with "erasure" named only as the supporting right. *Fix:* "…export or delete it."

- **[low]** The cancel-too-late race has no specced copy. On a stale read (`consumer-privacy.html` State B is stale by design), "Cancel deletion" can be shown after the window closed; the backend then rejects with "Deletion has already begun and cannot be cancelled." (`PartyAggregate.Handle(CancelPartyErasure)`). The spine's assertive-rejection pattern covers the mechanics but not this copy. *Fix:* add the rejection string (it is already plain-language and honest) to the "Erasure requested / in progress" state row as the specified inline reason.

- **[low]** No spine acknowledgement of the README launch gate for the Consumer portal. The README GDPR notice forbids regulated EU personal data until a production KMS replaces `LocalDevKeyStorageBackend`; the Consumer portal's whole purpose is inviting data subjects to submit and control personal data, and its copy claims verified permanence. No spine copy *contradicts* the caveat, but nothing prevents the portal going live under it either. *Fix:* one Foundation/rollout note in EXPERIENCE.md: consumer surfaces launch to real data subjects only once the production-KMS prerequisite (README GDPR notice / deployment-security-checklist) is met.
