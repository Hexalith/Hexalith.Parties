# Regulated Language Review — parties (GDPR)

_Run: 2026-09-08 · lens: regulated language_

## Overall verdict

The 2026-08-18 update landed every prior spine finding: Object is an honest contact path, restriction is visible to the data subject, erasure carries both cancel-window halves, a PII-free reference, consent-paused copy and the verbatim cancel-too-late rejection. The consumer register is plain, default-Off, and free of dark patterns. The remaining exposure is **over-promise and under-statement at the edges of the rights**: the completed-erasure sentence ("verified it's gone") is not true for legal-obligation retention and Art. 30 records; the Admin *Lift restriction* dialog lets a controller breach Art. 18(3) silently; and the only realistic post-erasure confirmation channel (re-sign-in a month later) lands the subject on a "we'll fix it" bug-shaped page. None of these is a copy typo — each needs one spine row plus a backend/PRD decision.

## Findings

### 1. Rights coverage

- **[medium]** Every "contact us" rights path is silent on when the subject hears back (EXPERIENCE Voice and Tone rows 5 and 8 — Object and restriction request; Help & contact IA row · Art. 12(3)). The spine correctly refuses a hard erasure SLA but a *response* deadline is a legal floor, not a promise, and its absence makes the contact path look like a black hole. *Where:* EXPERIENCE + backend. *Fix:* one Voice row: "We'll reply within a month. If it takes longer we'll tell you why." Route the Help & contact target to a DPO queue with a dated acknowledgement (architecture/PRD).
- **[high]** Admin *Lift restriction* has no inform-the-subject step (EXPERIENCE State Patterns "Restricted" row; Admin Lift confirm in `AdminPortalLabels.cs:260-263` "Lift processing restriction for the selected party?" · Art. 18(3)). Art. 18(3) requires the controller to inform the data subject *before* the restriction is lifted; the spine specs consumer-side copy while restricted but nothing stops a DPO lifting silently. *Where:* EXPERIENCE + backend. *Fix:* spec the Lift dialog: "Before lifting, the person must be told. Confirm you have informed them." with a required attestation checkbox (not typed name — reversible action); backend `LiftRestriction` should carry an `SubjectInformedAt`/channel field so the event is auditable (route to architecture).
- **[low]** Art. 19 recipient notification is unaddressed (Admin rectification/erasure; Flow 3 · Art. 19). The `PartyErased` subscriber contract cleans dangling refs, which is the technical half; no admin copy notes that downstream recipients are notified or listed. *Where:* backend/out-of-UX-scope. *Fix:* PRD note; optionally an Admin GDPR row "Recipients notified: n" once the projection exposes it.
- **[medium]** "Things we keep to run your account" states purpose and basis but not *how long* (EXPERIENCE Voice row 4; `consumer-privacy.html` State A datum rows · Art. 13(2)(a), 15(1)(d)). Retention period (or criteria) is a mandatory element of both the privacy notice and an access response. *Where:* EXPERIENCE + backend. *Fix:* add to the datum row contract: purpose · basis · "kept for: while your account is open + N years for tax records" (criteria acceptable where a period is unknowable); read model needs a retention descriptor per category (PRD).
- **[medium]** No surface names the controller, the DPO, or links the privacy notice (EXPERIENCE IA; Anti-patterns "policy detail is one click away" · Art. 13(1)(a)(b)). The spine promises policy is one click away but the IA has no row for it; Help & contact "routes to support/DPO" without saying the DPO is identifiable there. *Where:* EXPERIENCE. *Fix:* IA row or footer rule: "Privacy notice · Data controller: {tenant} · Contact the data-protection officer" rendered in the shell footer for the Consumer area (tenant-supplied values).
- **[low]** Object is presented in a 13px sub-line under one row (`consumer-privacy.html` State A `.basis.obj`; EXPERIENCE Flow 1 step 3 · Art. 21(4)). Art. 21(4) requires the right be brought to attention "explicitly … clearly and separately from any other information." Inline-under-the-row is defensible for one legitimate-interest item, marginal if more appear. *Where:* EXPERIENCE + mockup. *Fix:* rule: the object sentence renders at body size as its own paragraph inside the "Things we keep" card, not as a per-row footnote, once more than one legitimate-interest item exists.
- **[low]** Art. 22 is neither claimed nor excluded (EXPERIENCE Foundation · Art. 22). The product does no automated decision-making today; without a scope line, a future "risk score" or "service protection" (`ConsentLegitimateInterestTitle`) row could drift into 22 territory unnoticed. *Where:* EXPERIENCE. *Fix:* one Foundation sentence: "No automated decision-making or profiling within Art. 22 — any future scoring surface must add its own rights copy before shipping."

### 2. Consent semantics

Code already has `ConsentMarketingEmailsDescription` ("Messages about offers and campaigns.") and `ConsentBasisConsent`; the mock and spine are behind the code here. *Where:* EXPERIENCE + mockup. *Fix:* Component Patterns: every consent row = purpose title + one plain sentence of what it entails + state line; the "Things you control" card lead ("Consent is yours to give or take back, any time") is the shared basis statement, so a per-row "basis: consent" line is optional, but the description sentence is not. Update the mock rows.
- **[low]** Consent rejection copy drifts between spine and code (EXPERIENCE Flow 2 failure "We couldn't change this — please try again" vs `ConsentSaveFailure` "We couldn't save that consent choice. Please try again." · Art. 7(3)). Not verbatim-mandated; harmless drift, but the spine should decide whether this string is contract copy. *Where:* EXPERIENCE. *Fix:* either add it to the verbatim inventory or mark Flow 2's line as illustrative.

### 3. Erasure flow

- **[high]** "We've deleted your data and verified it's gone" over-promises against Art. 17(3) retention and the product's own residue (EXPERIENCE State Patterns erasure row (b), Flow 5 step 5; `consumer-privacy.html` State B "What's being deleted" lists every datum as "Scheduled for deletion" · Art. 17(3)(b), 30, 12(1)). The codebase has a `LegalObligation` lawful basis and a "Legal records" consent-page title; `PrivacyProcessingErasedMessage` admits "bounded processing records may remain"; the event store retains ciphertext and rejection events; backups exist. Telling the subject *all* their data is gone is a false statement about a legal right. *Where:* EXPERIENCE + mockup + backend. *Fix:* (a) completed copy: "We've deleted your personal data and verified it's gone. We keep only what the law makes us keep — {legal records category} — and a record that this deletion happened." (b) the "What's being deleted" card gets a second state per datum: "Kept — legal requirement" for legal-obligation items, stated *before* Confirm, not after. (c) Backend/PRD: the erasure status read must expose which categories were retained and why.
- **[high]** The realistic completion-confirmation path is broken by the No-party-binding copy (EXPERIENCE State Patterns "No party binding" and "Erased / Gone" rows; Flow 5 step 5 "while his session still lets him see it" · Art. 12(1), 17). Deletion "usually within 30 days" outlives any session; Marc will sign in later, his `party_id` claim will not resolve, and the spine routes him to `/no-party-binding`: "Your account isn't linked to a data record yet — contact us and we'll fix it." That tells a person whose erasure succeeded that something is broken and invites re-binding. PRD FR-Consumer-1 already requires "an erased self renders a PII-free tombstone"; code has `MyProfileDeletedTitle` "This profile was deleted." The spine's Erased/Gone row lists only Detail and picker surfaces. *Where:* EXPERIENCE + backend. *Fix:* extend "Erased / Gone" to the Consumer area: an erased self lands on a tombstone — "Your data was deleted on {date}. Reference {ref}. Nothing else is held." — never on No-party-binding; backend must distinguish "claim → erased party" from "claim → no party" (an erasure tombstone keyed by the hashed claim, route to architecture). Reword Flow 5 step 5 to the re-sign-in case.
- **[medium]** "You can cancel until deletion begins" never says when that is (EXPERIENCE Voice row 2, State Patterns erasure row (a), Flow 5 step 2 · Art. 12(1)). The subject cannot plan a reversible action against an undefined window; the Don't column bans conflating it with the 30 days but offers nothing instead. If the backend has a grace period, state it; if it does not, the window may be seconds and "reversible" is theatre. *Where:* EXPERIENCE + backend. *Fix:* decide the grace period (architecture/PRD) and state it honestly: "You can cancel for the next {N} days — after that deletion begins and can't be stopped." Dialog copy must carry the same figure.
- **[medium]** The consumer request reference and the Admin request identifier are not tied together (EXPERIENCE erasure row "PII-free request reference ('keep this number')"; `admin-parties.html` detail subtitle "subject erasure request #SR-4471" · Art. 12(6), 15). If Marc phones with his number and Priya's screen shows a different identifier, the reference is useless. *Where:* EXPERIENCE + backend. *Fix:* spec one reference format (ULID-derived, no name/date), minted at request time, shown identically on the consumer status page and the Admin GDPR panel; never logged with PII (project-context AC7).
- **[low]** Consumer stale mock lacks the mandated "as of HH:MM" (`consumer-privacy.html` State B freshness line vs EXPERIENCE Freshness indicator "always 'as of HH:MM'"; `admin-parties.html` has it). In an erasure-status context the as-of tells the subject whether "Cancel deletion" is still meaningful. *Where:* mockup. *Fix:* append "(as of 21:14)" to the State B freshness line.
- **[low]** Two export copy variants inside EXPERIENCE (Voice row 7 "Preparing your export — we'll have a download ready here. We'll show it when it's done." vs Flow 1 step 4 "Preparing your export — this can take a little while. We'll show it here the moment it's ready."; code uses the Flow 1 form). *Where:* EXPERIENCE. *Fix:* keep the Flow 1 form (already shipped, already PRD UX-DR15) and align the Voice row.
- Verified clean: start-not-finish, both halves stated, neutral tone, single Confirm without typed transcription for consumers, cancel-too-late verbatim from `PartyAggregate.cs:936`, "Keep my data" as the non-shaming dismiss label in code. No finding.

### 4. Transparency & timing

- **[medium]** Stale reads on `/me` and in the export are not framed for an Art. 15/20 response (EXPERIENCE State Patterns "Stale read", "Export preparing / ready" · Art. 15, 20). "Showing what we last knew — refreshing…" is fine for a UI; a subject screenshotting their profile as evidence, or downloading an export built from a degraded projection, receives an access response that may omit a rectification or show erased data. *Where:* EXPERIENCE + backend. *Fix:* the export-ready copy carries the projection freshness: "Your export is ready — data as of {HH:MM, date}." and the JSON package embeds `ProjectionFreshnessMetadata`; when the read is `Degraded`, disable Export with "We can't build a complete export right now — try again shortly" rather than silently exporting the last-known cache.
- **[medium]** Export scope, download validity, and file retention are unstated (EXPERIENCE Flow 1 steps 4–5; Voice row 7; code `PrivacyExportDescription` "the data connected to your signed-in account" · Art. 20(1), 5(1)(f)). Art. 20 covers data the subject provided under consent/contract; the copy implies "all my data." Nothing says whether the package persists server-side, for how long, or whether the link survives the session. *Where:* EXPERIENCE + backend. *Fix:* ready-state copy: "This file contains the data you gave us and the data we hold to run your account. The download is available for this sign-in only — you can request it again any time." Backend/PRD: confirm the package is not persisted (it is a projection read per project-context), so no retention statement is needed beyond that.

### 5. Admin-side language

- **[low]** Admin erase dialog body over-promises (`admin-parties.html` Alternate 1: "This permanently shreds Jordan Webb's personal data across all records." · Art. 17). The spine mandates only the title/instruction ("Erase party — irreversible. Type the name to confirm."). "Across all records" is a claim about subscribers and downstream systems the aggregate cannot verify; the verification report is the proof, not the dialog. *Where:* mockup + EXPERIENCE. *Fix:* "This destroys {name}'s personal data held here and starts verification. It can't be undone." and add the body sentence to the Voice row so code (`GdprErasureWarning`) converges.
- **[medium]** Restriction reason is free text with no guidance (Admin GDPR; `AdminPortalLabels.cs:229` "Restriction reason" · Art. 18(1), 9). A DPO typing "disputes accuracy of medical-leave record" puts special-category data into an event that replays into projections and audit trails forever. Art. 18(1) has exactly four grounds. *Where:* EXPERIENCE + backend. *Fix:* spec the reason as a bounded picklist — accuracy contested · processing unlawful, subject prefers restriction · needed for legal claims · objection pending (Art. 21(1)) — with an optional PII-free note field capped and flagged "no personal details"; badge tooltip shows the ground, not the note.
- **[low]** TenantUnavailable body asserts "your access is fine" (`admin-parties.html` Alternate 2; EXPERIENCE Voice row "Your workspace is still warming up — try again shortly"). Tenancy fails closed: a genuinely unknown tenant hits the same state, so the sentence can be false. The spine's mandated line is fine; the mock's body adds a guarantee. *Where:* mockup. *Fix:* "This usually clears a few seconds after a restart. If it doesn't, contact your administrator." Code (`TenantUnavailable` "Tenant context is unavailable") remains a queued fix.
- **[medium]** Admin-recorded consent has no evidence-of-consent capture (PRD FR-Admin-4 "record and revoke consent"; EXPERIENCE IA GDPR operations row "consent" · Art. 7(1), 4(11)). Consent recorded by staff on the subject's behalf is only valid if the controller can demonstrate the subject gave it; a bare "Record consent" button produces a `ConsentRecorded` event indistinguishable from a self-service one. *Where:* EXPERIENCE + backend (route to PRD). *Fix:* Admin record-consent dialog requires channel (signed form / verbal, dated / email) and date, stored on the event; consumer-side consent page shows "Recorded by staff on {date}" for such rows so the subject can dispute it.
- **[low]** Admin surfaces show a rights request as a ticket-style reference ("subject erasure request #SR-4471") next to the name and lifecycle badge. This is acceptable — PII-free, operator register — provided the reference never encodes the ground of the request (an Art. 9 leak if the reason were "health"). Folded into 5.2 and 3.4; no separate fix.
- Verified clean: typed-name confirm is Admin-only; erased row shows "(erased party)" not a name; "Restricted" badge carries text; audit label is neutral ("Audit trail"). Residual from prior review stands: typed name stays in-memory, never logged.

### 6. Forbidden / risky phrasing

- **[low]** "Your data is safe" as a failure reassurance is an implied security guarantee (EXPERIENCE Voice row 10, State Patterns "Transient failure", Flow 1 failure · Art. 5(1)(f)). In a rights context, after a failed export or erasure command, "safe" reads as a confidentiality/integrity claim the UI cannot make. *Where:* EXPERIENCE. *Fix:* "Nothing about your data has changed — try again." (states the true fact: the command did not apply).
- **[low]** DESIGN.md Do's and Don'ts has no symmetry rule for consent/erasure controls (DESIGN.md Do's and Don'ts; EXPERIENCE Anti-patterns "consent dark patterns" · Art. 7(3), EDPB dark-patterns guidelines). The behavioral ban lives in EXPERIENCE; the visual layer that a developer actually applies (button appearance, size, colour) says only "reserve the danger fill." `consumer-privacy.html` is fine today (Export primary, Delete danger-outline, equal size). *Where:* DESIGN. *Fix:* add a row — Do: "Grant/withdraw and keep/delete pairs get equal size and equal visual weight; the dismiss in a rights dialog is a real Outline button." Don't: "Make the keep/stay-opted-in option Primary while the exercise-the-right option is a text link."
- Verified clean: no "we may", no "anonymous" (erased rows are tombstones, correctly pseudonymous residue), "permanent" appears only where crypto-shred makes it true, no confirmshaming, "Keep my data" is neutral, no pre-selected choices.
