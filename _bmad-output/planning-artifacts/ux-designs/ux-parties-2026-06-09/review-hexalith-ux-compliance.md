# Hexalith UX Compliance Review — parties

_Run: 2026-09-08 · lens: FrontComposer + Fluent UI Blazor V5 rules (hexalith-ux-instructions.md)_

Sources checked: `references/Hexalith.AI.Tools/hexalith-ux-instructions.md` and the
"User Interface & UX" section of `hexalith-llm-instructions.md`; FrontComposer shell
source at the pinned submodule (`references/Hexalith.FrontComposer/src/Hexalith.FrontComposer.Shell`,
`Contracts`, `Contracts.UI`) and its `FluentConformanceTests.cs`; the Fluent UI Blazor V5
package actually pinned by `Hexalith.Builds` (`Microsoft.FluentUI.AspNetCore.Components
5.0.0-rc.5-26219.1`, type/parameter names read from the package XML docs); the spines,
`.memlog.md`, `index.md`, and `mockups/*.html`; a static spot-check of
`src/Hexalith.Parties.{UI,AdminPortal,ConsumerPortal,Picker}` and
`tests/Hexalith.Parties.UI.Tests/AccessibilityStyleGuardTests.cs`.

## Overall verdict

The spine pair has the right posture — "delta only, inherit Fluent 2 + FrontComposer",
tokens referenced by name, an as-is V5 component inventory that is real — and it
correctly names most shell behaviours it leans on (skip links, Ctrl+K / Ctrl+, theme
Light/Dark/System, policy-gated `FluentNav`, `--fc-color-*`, `--fc-spacing-unit`,
`Typography.AppTitle`). It does **not** transmit three hard rules a story-dev must obey
(the full legacy-token family ban, the `FluentAccordion` page-sections rule, and an
enforceable conformance guard with an allowlisted backlog), and it mandates one
behaviour FrontComposer does not expose (a per-area density posture). Several domain
components are specified by ARIA outcome plus token colours rather than by a V5
component and its parameters, which pushes devs toward the CSS overrides the rules
forbid — the shipped portals already show that drift (≈70 legacy-token hits in eight
`.razor.css` files, none covered by the style guard).

## Findings

### 1. Inheritance posture

- **[high]** Per-area density is specified as inherited shell behaviour ("Admin runs at comfortable `--fc-spacing-unit: 4px`; Consumer at roomy `6px`", DESIGN §Layout & Spacing / frontmatter `spacing.density-*`; EXPERIENCE §Foundation "Defaults: Admin density comfortable, Consumer roomy"). FrontComposer density is one **global** posture resolved by `DensityPrecedence.Resolve` (`Shell/State/Density/DensityPrecedence.cs`): viewport ≤ Tablet → Comfortable, else user preference, else `FcShellOptions.DefaultDensity`, else factory (`DensitySurface.Default` → **Compact**, not Comfortable). It is applied once on `<body data-fc-density>` by `FcDensityApplier`. There is no per-area / per-route API; the only per-element mechanism is hard-coding `[data-fc-density]` on a DOM root (`fc-density.css` lines 13–15), which the resolver documents as reserved for "custom components that want a locked density" and which would silently override the user's own Settings choice (Ctrl+,) — contradicting the spine's own "theme follows the OS until the user chooses" ethic. `.memlog.md` has already queued "wire `--fc-spacing-unit` density per area" as a code fix, i.e. the violation is about to be built. *Where:* EXPERIENCE (Foundation) + DESIGN (Layout & Spacing, frontmatter) + **FrontComposer (platform request)**. *Fix:* state that density is user-owned via the shell; set `FcShellOptions.DefaultDensity = Comfortable` for the deployment; either drop "Consumer roomy" or record it as a FrontComposer request (area/route-scoped `DensitySurface`); add a Don't row: "never set `--fc-spacing-unit` or `data-fc-density` in module CSS/markup".
- **[medium]** `typography.body-consumer` declares literal `fontFamily / fontSize: 16px / fontWeight: '400' / lineHeight: '1.5'` and §Typography says the Consumer area "bumps body to 16px at line-height 1.5" without naming the allowed mechanism. Under "no theme redefinition" a dev will write an area-wide `font-size` / `line-height` rule (the shipped `ConsumerRouteShell.razor.css` does exactly this with `--type-ramp-*`). `1.5` is also not the Fluent pair for `--fontSizeBase400` (`--lineHeightBase400` is 22px ≈ 1.375), so it is a new ramp, not a reference. *Where:* DESIGN. *Fix:* express the delta as `FluentText Size="TextSize.Size400"` (plus `--lineHeightBase400` if a container rule is unavoidable) for consumer body copy; delete the `1.5` literal; or park the area-wide type scale as a FrontComposer request.
- **[low]** Shell dimensions are restated with numbers the spine doesn't own: "Navigation 220px expanded / 48px collapsed". At the referenced FrontComposer source the rail is **72px labelled / 48px collapsed** (`FrontComposerShell.razor.cs` `NavigationWidth`); the 220px appears in every mock. Header 48px (`--layout-header-height`, `FrontComposerShell.razor.css` line 9) and `Padding.All3` are correct. *Where:* DESIGN (Layout & Spacing) + mockups. *Fix:* "nav width inherits the shell"; remove px from the spine and mock captions.
- **[low]** `rounded.*` literals ("named here only for prose reference") and `full: 9999px` for `--borderRadiusCircular` (Fluent 2 value is 10000px). Harmless, but each literal is a copy-paste seed and the Do/Don't row itself says never redeclare Fluent 2 properties. *Where:* DESIGN frontmatter. *Fix:* keep token names only, drop px values.
- **[low]** V4/FAST vocabulary survives in the theme guidance: "design-token API", "`baseLayerLuminance`", "Set theme via `IThemeService` / design-token API". V5's API is `IThemeService.SetThemeAsync(new ThemeSettings(Color, HueTorsion, Vibrancy, Mode, IsExact))` (verified in package XML) and the **shell owns that call** (`Shell/State/Theme/ThemeEffects.cs`, `FcSystemThemeWatcher.razor.cs`, `FrontComposerShell.razor.cs` line 678). Modules should never call it. *Where:* DESIGN (Colors, Do/Don't). *Fix:* "Theme is set by the shell from `FcShellOptions.AccentColor`; modules do not call `IThemeService` and do not set Fluent 2 custom properties."
- Verified as correctly inherited (no finding): `--fc-color-{accent,neutral,success,warning,danger,info}` (`FrontComposerShell.razor.css` lines 10–15), `--fc-spacing-unit` (`wwwroot/css/fc-density.css`), `--fc-page-max-inline-size` 75rem (`FrontComposerShell.razor.css` line 31 — applied only when a page declares `<FcPageLayout Mode="Constrained">`), `Typography.AppTitle` = `FcTypoToken(Size700, Bold, H1)` (`Contracts.UI/Rendering/Typography.cs` line 38), `FcShellOptions.AccentColor` default `#0097A7` (`Options/FcShellOptions.cs` line 131).

### 2. Forbidden tokens & practices

- **[high]** The FAST ban is transmitted too narrowly. DESIGN Don't: "Style any surface against legacy FAST `--*-rest` tokens". The rule bans the **families** `--type-ramp-*`, `--neutral-*` (incl. `--neutral-foreground-hint`), `--accent-*`, `--neutral-fill-*`, `--palette-*`. Shipped code today: `MyPrivacyPage.razor.css` (13 hits), `MyProfilePage.razor.css` (13), `ConsumerRouteShell.razor.css` (9), `PartiesAdminPortal.razor.css` (16), `PartyGdprOperationsPanel.razor.css` (7), `CreateEditPartyPage.razor.css` (6), `EditMyProfilePage.razor.css` (4), `MyConsentPage.razor.css` (1) — many are `--type-ramp-*-font-size` / `--neutral-foreground-hint`, which a `--*-rest` reading lets through. *Where:* DESIGN (Do/Don't) + code. *Fix:* quote the rule's families verbatim in the Don't row and mandate the FrontComposer `LegacyFluentToken` + `LegacyErrorToken` regexes (`tests/Hexalith.FrontComposer.Shell.Tests/Governance/FluentConformanceTests.cs` lines 41–55) as the guard.
- **[medium]** Freshness indicator is specified as "a small status dot + label" with per-state token colours (`components.freshness-indicator.*`). That is a mandate for a hand-rolled `span.dot` — precisely what all five mocks do (`.dot.ok/.stale/.info`). V5 provides `FluentBadge` (`BadgeAppearance.Tint`, `BadgeShape.Circular`, `Color=BadgeColor.Success|Warning|Informative`, `IconStart`), `FluentPresenceBadge`, and `FluentStatus` (status icons + colours) — all verified in the rc.5 XML. *Where:* DESIGN (Components). *Fix:* name the primitive ("`FluentBadge Tint/Circular` with `BadgeColor` + text, or `FluentIcon Color=Color.Success/Warning/Info` + `FluentText`; never a custom dot") and move the token list to a comment.
- **[medium]** Party picker: `<hexalith-party-picker>` is a custom element with raw `<input>`/`<button>` and shadow-root CSS (`src/Hexalith.Parties.Picker/Components/PartyPicker.razor` lines 9, 27, 52, 61). V5 has `FluentAutocomplete<T,U>` and `FluentCombobox<T,U>`, so "reuse over hand-rolling" requires either a written justification or a replacement inside Blazor forms. The spine says "used as-is behaviorally" and celebrates the re-skin, but never states why a Fluent combobox is not the answer (cross-host embedding? the 12-state machine?). *Where:* DESIGN + EXPERIENCE (Component Patterns) + code. *Fix:* either scope the custom element to non-Blazor hosts and require `CreateEditPartyPage` to use `FluentAutocomplete`, or document the carve-out (rationale + allowlist entry in the conformance guard) so a reviewer can tell exception from drift.
- **[medium]** "Bind **link text** to `{colors.brand-fill}` — links are text" (DESIGN Do row, Colors §Avoid) reads as `a { color: var(--colorBrandBackground) }`, i.e. recreating a foreground role in CSS. V5 has `FluentLink` (and `FluentAnchorButton`), which already use the brand foreground tokens. *Where:* DESIGN. *Fix:* "Links are `FluentLink`; never set link colour in CSS. If a raw `<a>` is unavoidable (nav link carve-out), bind `color` to `--colorBrandForegroundLink`."
- **[low]** Focus ring: "visible `--colorStrokeFocus2` focus ring styled inside the shadow root" and the shipped `MainLayout.razor.css` `::deep :where(a, button, input, …):focus-visible { outline: … --colorStrokeFocus2 }` re-draw a ring Fluent components already provide. The rule allows this only for elements Fluent does not own (custom element internals, route `<h1>`, raw `<a>`). *Where:* DESIGN (Colors §Focus) + code. *Fix:* "Fluent components keep their own focus ring; only non-Fluent focusables get an app-owned `--colorStrokeFocus2` outline."
- **[low]** GDPR danger fill: V5 `ButtonAppearance` is Default/Primary/Outline/Subtle/Transparent (verified) — there is no danger variant, so token-based CSS is the legitimate fallback, but the spine does not say so and omits hover/pressed tokens. The shipped `PartyGdprOperationsPanel.razor.css` fell back to `--error-fill-rest, #b10e1c`. *Where:* DESIGN (Components). *Fix:* label it "allowed fallback — no V5 parameter exists", give the full token set (`--colorStatusDangerBackground3`, `…Background3Hover`, `…Background3Pressed`, `--colorStatusDangerForegroundInverted`), and note V5 `FluentButton` also exposes `BackgroundColor` / `Color` parameters (see Unverified) as the preferred parameter route if they accept token values.
- Do's and Don'ts sufficiency: the table is good on colour semantics and AA, but it lacks rows a dev or test can act on for (a) the full legacy-token families, (b) "custom CSS only for layout / no-component features", (c) "never override a Fluent component's styles via `::deep` / `Class` — use parameters", (d) "never set shell tokens (`--fc-*`, `--layout-*`) in module code", (e) the `FluentAccordion` page-section rule.

### 3. Component mapping

- **[medium]** Party-state badge: "Built on `FluentBadge` (`Appearance.Tint`)" — the V5 enum is `BadgeAppearance.Tint`; colour is a parameter (`Color="BadgeColor.Success|Warning|Danger|Subtle"`) and shape is `BadgeShape.Circular` (all verified). The frontmatter instead binds each state to a `--colorStatus*Foreground1` **token**, which invites CSS on the badge (forbidden) rather than the parameter. The shipped `src/Hexalith.Parties.UI/Components/Shared/PartyStateBadge.razor` already does it correctly via parameters — but uses `BadgeShape.Rounded`, not the spine's pill. *Where:* DESIGN (frontmatter `components.party-state-badge`, §Components). *Fix:* specify `BadgeAppearance.Tint · BadgeShape.Circular · BadgeColor {active→Success, inactive→Subtle, restricted→Warning, erased→Danger}`; demote token names to "what those map to".
- **[low]** Behavioural rows describe ARIA outcomes without the V5 component that provides them, so a dev may hand-roll: consent control → `FluentSwitch` with `CheckedMessage` / `UncheckedMessage` ("Off — you won't get marketing emails"); inline validation → `FluentField` `Message` / `MessageState` (+ `FluentValidationSummary`); Person/Organization `radiogroup` → `FluentRadioGroup<T>`; typed-erase confirm → `FluentTextInput` inside `FluentDialog`. *Where:* EXPERIENCE (Component Patterns, Accessibility Floor). *Fix:* add a "V5 component" column.
- **[low]** Command-result status region: DESIGN says `FluentMessageBar`, EXPERIENCE says inline `role=status aria-live=polite` / `role=alert`. V5 `FluentMessageBar` exposes `Intent` (Info/Success/Warning/Error) and an `AriaLive` parameter (verified) — the spines are compatible but should say "`FluentMessageBar Intent=Info` for erasure acks; `AriaLive` polite for status, assertive for rejections" so nobody builds a second live region. *Where:* EXPERIENCE. 
- Verified real in `Microsoft.FluentUI.AspNetCore.Components 5.0.0-rc.5-26219.1`: `FluentLayout`, `FluentLayoutItem`, `FluentProviders`, `FluentNav`, `FluentNavItem`, `FluentNavCategory`, `FluentDataGrid<T>`, `TemplateColumn<T>`, `FluentTextInput`, `FluentSelect<T,U>`, `FluentButton` (`ButtonAppearance.Outline` ✓), `FluentBadge`, `FluentMenu`, `FluentMenuButton`, `FluentStack`, `FluentText` (`Size`/`Weight`/`Color`/`As` ✓), `FluentSpacer`, `FluentSwitch`, `FluentDialog` (`Modal`, `PreventDismissOnEscape`), `FluentMessageBar`, `FluentSkeleton`, `FluentAccordion`/`FluentAccordionItem`, `Padding.All3`, `IThemeService`. No V4 leftovers in the inventory itself; the only V4-isms are the enum name above and the theme vocabulary in §1.

### 4. Shell contract

- Verified — the shell provides what EXPERIENCE assumes: skip links to content and nav as first tab stops (`FrontComposerShell.razor` lines 35–41); `Ctrl+K`/`Meta+K` palette and `Ctrl+,`/`Meta+,` settings (`Shell/Shortcuts/FrontComposerShortcutRegistrar.cs` lines 73–95; also `g h` home and `/` grid filter); theme Light/Dark/System (`FcThemeToggle`, `FcSystemThemeWatcher`, `ThemeEffects.cs`); nav auto-populated from registered manifests and gated per entry by `<AuthorizeView Policy="@entry.RequiredPolicy">` (`FrontComposerNavigation.razor` lines 43–47); nav suppressed to hamburger at Tablet/Phone (`FrontComposerShell.razor.cs` `IsSubCompactDesktopViewport`); header 48px; content `Padding.All3`; `role=status`/`aria-live` primitives (`FcProjectionConnectionStatus`, `FcPendingCommandSummary`, `FcLifecycleWrapper` with `AriaRole`/`AriaLive`, `FcDensityAnnouncer`); forced-colors handling for skip links (`wwwroot/css/fc-shell.css` line 24); reduced-motion in `fc-projection.css`.
- **[medium]** EXPERIENCE re-specifies page-level state routing generically ("Cold load → skeleton", "Stale read → banner + last-known", "Display-name-only") without pointing at the shell primitives that already implement it: `FcAggregateDetailPage<TItem>` / `FcAggregateListPage` route `FcAggregateDetailState` (Loading/Ready/Stale/Degraded/…) with a banner slot for stale/degraded (`Shell/Components/Layout/FcAggregateDetailPage.razor.cs`), `FcProjectionLoadingSkeleton` (`role=status aria-busy`), `FcProjectionEmptyPlaceholder`, `FcLifecycleWrapper`, and `FcPageLayout Mode=Constrained` for the Consumer single-column measure. A dev following the spine will hand-roll these. *Where:* EXPERIENCE (State Patterns, Responsive). *Fix:* map each State Patterns row to the FrontComposer component/state it should use; say "Consumer pages declare `<FcPageLayout Mode="Constrained">`" instead of "inherits `--fc-page-max-inline-size`".
- **[high — same as §1 first finding]** Per-area density posture is not a shell capability. *Where:* FrontComposer (platform request) + EXPERIENCE/DESIGN.
- **[low]** "Modal depth ≤ 1" and "`Esc` closes any `FluentDialog`" are consistent with `IDialogService.ShowDialogAsync` usage in the shell (`FrontComposerShortcutRegistrar.OpenPaletteAsync`); note that `FluentDialog.PreventDismissOnEscape` exists and must stay false for the typed-erase dialog. *Where:* EXPERIENCE (Interaction Primitives).

### 5. Mockups as risk

- **[medium]** Neither spine states the no-port rule. "Spine wins on conflict with any mock" is a precedence rule, not "do not port this CSS"; only `index.md` line 6 says "illustrative". The mock headers actively invite porting: "Tokens are Fluent 2 values; names in comments map to `--colorXxx` custom props" (`admin-parties.html` line 18). Copy-paste hazards present in the mocks: hard-coded badge tints `.b-active #e7f3e7`, `.b-restricted #fff9f5`, `.b-erased #fbe9e9`, `.b-inactive #eef0f1` (lines 75–78); custom `.dot` freshness (65–66); custom `.sw` switch (`consumer-privacy.html` 61–64) where `FluentSwitch` exists; custom `.dialog`/`.scrim` (97–102) where `FluentDialog` exists; `.toast` with hard-coded `#0b3b15` / `#1f2937` (`admin-parties.html` 91, `consumer-privacy.html` 68) although the spine bans toasts and renamed the pattern "status region"; `.nav a.active` / `.grow.sel` selection by `box-shadow: inset 3px` + tint (51, 71) which DESIGN's own Don't row forbids as forced-colors-fragile; `220px` nav column (42). *Where:* mockup (all five) + one line in DESIGN §Components. *Fix:* add a first-line comment and visible caption to every mock — "Illustrative only. Build with `FluentBadge` / `FluentSwitch` / `FluentDialog` / `FluentMessageBar` / `FluentNav`; do not port these styles or hex values" — rename `.toast` → `.status-region`, and in DESIGN §Components add: "Mocks are raw HTML for composition only; implementation uses the components named above, never the mock CSS."

### 6. Enforceability

- **[high]** No automated guard is mandated by the spines, and the one that exists is too narrow to enforce them. `tests/Hexalith.Parties.UI.Tests/AccessibilityStyleGuardTests.cs` scans only `src/Hexalith.Parties.UI/Components` (`AppOwnedRoots`) for raw colour literals (`#`, `rgb(`…) and `outline:none` without `:focus-visible`; it has no legacy-token regex, no raw `<button>/<input>/<select>/<textarea>` check, no `FluentAccordionItem Heading=` (v4) check, and no allowlist. AdminPortal, ConsumerPortal and Picker are unscanned and are where the ≈70 legacy-token hits live. FrontComposer already ships the reference implementation — `FluentConformanceTests.cs` (`RawInteractiveControl`, `LegacyFluentToken`, `LegacyErrorToken`, `AccentSurfaceBackgroundDeclaration`, `V4AccordionHeadingAttribute`, dead-scoped-class detection, allowlists that may only shrink). The rule's last bullet ("files still using legacy tokens must be tracked as an explicit, allowlisted migration backlog — not silently exempted") is therefore unmet. *Where:* DESIGN (Do/Don't + a short "Enforcement" paragraph) + code. *Fix:* DESIGN mandates a Fluent-conformance test across all four UI projects mirroring FrontComposer's, seeded with the eight current offenders as the shrinking backlog; `.memlog.md` should promote "extend a11y style-guard roots" from queued to required by the spine.
- **[high]** Page-sections rule is absent from both spines and from the code (no `FluentAccordion` in `src/`). Surfaces that qualify: Admin GDPR operations (five sibling titled sections), Party detail aside (Details + GDPR operations), Consumer "My data & privacy" ("Things you control" / "Things we keep" / actions), Consumer profile (if it groups sections). Without the rule, a dev will build `<section><h3>` stacks as the mocks do (`admin-parties.html` `.sec h4`). *Where:* DESIGN (Components) + EXPERIENCE (IA / Component Patterns) + code. *Fix:* add the rule verbatim; give a per-surface map of which sections go in the accordion, which stay outside (title, freshness bar, toolbar, the single primary grid/form), and which item is expanded by default; note V5 uses `Header=` (v4 `Heading=` is silently dropped — `FluentConformanceTests.V4AccordionHeadingAttribute`).
- **[low]** Existing guard asserts `MainLayout.razor.css` **contains** an app-owned `::deep :focus-visible` ring (`App_owned_content_styles_stay_scoped_to_a_rendered_element`). That test bakes in the ring-recreation flagged in §2; when the spine clarifies scope (non-Fluent focusables only), the assertion should be narrowed with it. *Where:* code.

## Unverified claims

- **`FluentButton.BackgroundColor` / `Color` parameters** exist in the rc.5 XML, but I did not confirm their types or whether they accept `var(--colorStatusDangerBackground3)` token strings. If they do, the GDPR danger fill can be parameter-driven and needs no CSS at all — the spine should prefer that route.
- **`FluentMessageBar` live-region semantics**: the `AriaLive` parameter is confirmed; whether the rendered element also carries `role="status"` / `role="alert"` (vs. only `aria-live`) was not checked in DOM output. EXPERIENCE's role split may need a wrapper if not.
- **Token emission**: Fluent 2 defines `--colorStatusDangerForegroundInverted`, `--colorStatusDangerBackground3Hover/Pressed`, `--colorStatus*Background1`; I did not confirm the V5 theme script emits every one as a document-level custom property. Devs should verify in DevTools before binding.
- **`--borderRadiusCircular`** is 10000px in the Fluent 2 token set; DESIGN says 9999px. Cosmetic.
- **Nav width** (72px labelled / 48px rail) was read from the FrontComposer submodule HEAD; the parties repo consumes the packaged `Hexalith.FrontComposer.Shell 4.4.0` (`AccessibilityStyleGuardTests.PackagedFrontComposerShellVersion`), which may differ. Either way the spine should not pin a number.
- **`FluentSwitch`** emitting `role="switch"` + `aria-checked` and **`FluentDialog`** focus trap/restore are expected from the underlying `<fluent-switch>` / `<fluent-dialog>` web components; not verified against rendered DOM.
- **Dark-mode AA** of the derived brand ramp (`ThemeSettings` with default `HueTorsion`/`Vibrancy` = 0, `IsExact` = false) — the spine already treats it as an acceptance check; not evaluated here.
- **Fluent V5 combobox parity** with the picker's 12-state machine (`Degraded`/`LocalOnly`/`Gone`…) — I confirmed `FluentAutocomplete<T,U>` / `FluentCombobox<T,U>` exist, not that they can host every state; that is the carve-out argument the spine should write down if it keeps the custom element.
