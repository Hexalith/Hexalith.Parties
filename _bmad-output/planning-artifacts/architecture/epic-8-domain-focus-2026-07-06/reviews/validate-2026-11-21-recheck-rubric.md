### Medium · Subscriber acknowledgement can suppress required redelivery

The team overview (§7, line 259) tells subscribers to always return HTTP 200. The same overview (§8, line 290), I7 (lines 232–239) and the November 20 erasure decision (line 38) require a durable consumer that recovers from failed appends and redelivery. If transient processing fails before work is durably recorded, acknowledging the event can end broker retries and leave mandatory downstream cleanup incomplete. The publishing guide (lines 82–88) explicitly relies on failed deliveries to reach retries and dead letters. The selected SDK’s own subscriber also acknowledges completed, duplicate and permanently skipped deliveries but returns retryable responses for transient outcomes (lines 63–78). Amend §7 to distinguish successful processing, durable handoff, intentional permanent skips and transient failures that still need redelivery. ### Medium · Successor security parity omits the receiver’s authentication checks

I1 enumerates the service-invocation ACL and calls tenant-event delivery “the other ingress” (lines 135–169). The I1 evidence row names ACL tests and an external tuple check (line 513). The current host also has sidecar discovery and actor callbacks protected by the authenticated Dapr application channel. Gateway operations additionally require a signed workload assertion for the receiver and operation (`Program.cs`, lines 71–83). Correct ACL tuples alone cannot qualify those receiver checks after a topology move. State both receiver guarantees in I1/I2, name callback traffic separately from the gateway route list, and add equivalent receiver-side verification to the successor evidence row. The existing topology isolation test illustrates the distinction on the sample receiver (lines 204–231).
