## Findings

### F1 — HIGH: Builds catalog pin `17b1c7a…` is not the committed gitlink
Spine §7 I4 (line 181) and `PlatformApiPrerequisitesTests.cs:18` pin the Builds catalog to `17b1c7aae3e1854e464f17bd88d527f8350ea203`, and the Story 8.3 matrix (line 65) records "Root gitlink and checkout `17b1c7a…`". In reality only the working-tree **checkout** is at that SHA; the gitlink recorded in HEAD and the index is `6b7807533cea31aa7592450742a5c94dd1bc1d9f` (`git ls-tree HEAD references/Hexalith.Builds`; `git status` shows `M references/Hexalith.Builds`, i.e. an uncommitted bump). The matrix's own words — "Root gitlink and checkout" — are therefore false at the committed state. On a fresh clone of HEAD, `AssertGitlinkAndCheckout`'s unconditional `DescribeIdentityGap(checkout, 17b1c7a…)` check (`PlatformApiPrerequisitesTests.cs:1452`) would fail (checkout would be `6b78075…`), so the closure evidence the spine cites is only green on this working tree. **Remedy:** commit the submodule bump (spine text needs no change), or if the bump is not intended, the spine/matrix/test pin must be corrected to the committed SHA. (Same working-tree-vs-HEAD drift exists for FrontComposer/Memories/PolymorphicSerializations, but the spine pins none of those.)

### F2 — MEDIUM: the gitlink assertion is OR-shaped and masks HEAD/checkout divergence
`AssertGitlinkAndCheckout` (`PlatformApiPrerequisitesTests.cs:1442-1450`) accepts a match against **any** of HEAD gitlink, index entry, or checkout HEAD. That is exactly the shape that lets F1 pass locally while the committed superproject disagrees. Contrast `AssertPayloadProtectionEvidence` (`:1261-1267`), which asserts `ls-tree HEAD` strictly for EventStore. For "immutable consumption proof" (the test's own words at `:1454`) the gitlink check should require HEAD **and** checkout to agree, as the EventStore-specific path already does. Not a spine defect per se, but the spine's I4 claim of test-pinned identities inherits this weakness.

### F3 — MEDIUM: I13 "purge FAST/v4 tokens" is not fully realized in retained UI
Three retained CSS files still consume FAST/v4-convention design tokens (`--neutral-fill-stealth-rest`, `--neutral-fill-rest`, `--error-fill-rest`, `--warning-fill-rest`): `PartiesAdminPortal.razor.css:75,80,85`, `CreateEditPartyPage.razor.css:51`, `MyProfilePage.razor.css:143`. Nothing in `src/` defines these custom properties, and the Fluent UI v5 RC pin (Fluent 2, `--colorNeutral*`-style tokens) does not emit them — so four of the five usages silently take their fallback, and `PartiesAdminPortal.razor.css:75` has **no** fallback (the declaration is invalid at computed-value time). `AccessibilityStyleGuardTests.cs` contains no FAST-token guard, so the §7 claim that `MainLayoutAccessibilityTests`/`PartiesAccessibilitySpecimenTests` make I13 "executable" does not extend to token purity. Either purge the residual tokens or record them as an explicit `8.9-frontcomposer-ui-consolidation` deferral in the I13 row.

### F4 — LOW: §7 closure evidence relies on untracked files
`DocumentationFitnessTests.cs`, `EpicEightClosureFitnessTests.cs`, and `ClosureDeferral.cs` (all under `tests/Hexalith.Parties.Tests/FitnessTests/`) are untracked (`??` in `git status`), and the §7 map plus several doc updates are uncommitted modifications. The spine's 2026-08-18 closure map is therefore a snapshot of an uncommitted working tree; the evidence is real but not yet durable. Committing the pending work resolves F1 and F4 together.

### F5 — LOW: `ReadModelWritePolicy` is a static class, listed among "target abstractions"
I10 groups `ReadModelWritePolicy` with four interfaces as "target abstractions". It exists, but as `public static partial class ReadModelWritePolicy` (`references/Hexalith.EventStore/src/Hexalith.EventStore.Client/Projections/ReadModelWritePolicy.cs:28`) — a policy helper, not an abstraction/seam. Cosmetic; the name is real and reality-checked, only the categorization overstates it.

### F6 — LOW: §7 I11 attributes ULID preservation to a test that does not mention ULID
The §7 I11 row credits `IdentifierHygieneFitnessTests` and `PartyAggregateIdentifierTests` with preserving "ULID-compatible and GUID-shaped replay". `IdentifierHygieneFitnessTests` is a negative guard (no `Guid.*` parsers) and `PartyAggregateIdentifierTests.cs` contains no ULID reference; the positive ULID acceptance coverage actually lives in `IdentifierValidatorTests.cs` and `PartyAggregateCompositeTests.cs`. The invariant is covered by the suite, but the evidence map names the wrong witnesses.
