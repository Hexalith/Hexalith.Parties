## Findings

### F-1 — I7 enumerates MCP `delete_party` as an erasure door; the tool is soft deactivation and says so
- **Severity:** High
- **Disposition if updating:** autofix
- **Evidence:** Spine I7 (lines 181-188): "Erasure mutation paths are the closed set **Admin `EraseParty`, Consumer `RequestMyErasure`/`CancelMyErasure`, MCP `delete_party`**; every path applies the same aggregate command, the same D7 verification, and the same I10 tombstone … must not grow a fourth door." Source: `src/Hexalith.Parties.Mcp/Tools/PartiesMcpTools.cs:391` `[Description("Soft deactivates a Parties record for MVP delete intent. This tool does not perform GDPR erasure.")]`; `:421` `commandClient.DeactivatePartyWithResultAsync(partyId, …)`; `:415-416` result `operation = "soft-deactivation", gdprErasurePerformed = false`; `:490,497` the same flag on every branch. No `EraseParty` sender exists under `src/Hexalith.Parties.Mcp`. The wording was lifted from `reviews/review-2026-09-08-adversarial.md:161` (P18 "Close-with") and memlog line 35, neither of which cites the tool's source; the adversarial P18 itself only quoted spec-8-8's tool-name list (`spec-8-8-…:28`).
- **Why it matters:** The amendment turned an adversarial hypothesis into a committed fact that the code contradicts. Today the false clause makes I7 look stricter than reality, but it creates two live hazards: (a) an 8.8 executor reading "every path applies the same aggregate command" can conclude `delete_party` *must* be wired to `EraseParty` to become I7-compliant — silently opening the third door the adversarial lens feared, with no I13 typed-name confirmation and no ledger row; (b) "must not grow a fourth door" mis-counts the doors, so the ledger-governed enumeration (the whole point of the I7 tightening) starts from a wrong baseline. The fix is one sentence: enumerate two doors (Admin, Consumer), state that MCP `delete_party` is soft deactivation (`DeactivateParty`) and is **not** an erasure path, and that promoting it would be an I7 door addition requiring the 8.3-ledger row.

### F-2 — The "last authorized set" is internally unsatisfiable: Builds `35c3d1e5` pins FrontComposer 4.3.0, not the 4.4.0 the matrix, the signoff, and the fitness test assert
- **Severity:** High
- **Disposition if updating:** discuss (tree decision), then autofix the I4 row
- **Evidence:** `git -C references/Hexalith.Builds show 35c3d1e5:Props/Directory.Packages.props` line 9 → `HexalithFrontComposerVersion … 4.3.0`. `git diff 35c3d1e5 a32cb422` → exactly one changed line, 4.3.0 → 4.4.0 (`a32cb42 fix: update HexalithFrontComposerVersion to 4.4.0`). Yet: 8.3 matrix line 72 says the `35c3d1e5` catalog "selects … FrontComposer `4.4.0`"; matrix line 73 and `PlatformApiPrerequisitesTests.cs:28` call `4.4.0` "the packaged identity that CI and the released container use"; `.gitlink-signoff.tsv:85-86` comments "FrontComposer package identity moves to published 4.4.0" while authorizing `35c3d1e5` (`:87`); `PlatformApiPrerequisitesTests.cs:23` pins `BuildsSha = 35c3d1e5` **and** `:693` asserts the live catalog contains `HexalithFrontComposerVersion … 4.4.0`. Spine §7 I4 presents the set as consistent and offers "restore the gitlink to `35c3d1e5`" as one of two remedies; §10 calls the tree condition "not spine-fixable".
- **Why it matters:** The spine (and V27/V29 before it) reality-checked *that* HEAD drifted past the pin, but not *what the pin selects*. Restoring `35c3d1e5` — the remedy the spine prints first — would not make the I4 executable surface green (the `:693` catalog assertion fails at 4.3.0) and would falsify matrix rows 72-73. Conversely `a32cb422` is precisely the commit that makes those documents true; it is missing only its signoff line and test constant. The row should say so: the authorized pin and the authorized catalog claim disagree, so only remedy (b) — sign off and stamp `a32cb422` — restores a consistent identity set. Until then "I4 — Executable" describes a test that cannot pass at any single Builds gitlink, which is an I16 stop by the spine's own rule and should be worded as one.

### F-3 — I7 consumer door names are not identifiers in the tree, and "same aggregate command" is inexact for the cancel path
- **Severity:** Medium
- **Disposition if updating:** autofix
- **Evidence:** No type, route, or tool named `RequestMyErasure` / `CancelMyErasure` under `src/` (`rg` → only `…Async` methods). Real surface: `ISelfScopedPartiesClient.RequestMyErasureAsync` / `CancelMyErasureAsync` (`src/Hexalith.Parties.UI/Services/ISelfScopedPartiesClient.cs:46,49`), implemented at `SelfScopedPartiesClient.cs:73-77` by delegating to `gdprClient.RequestErasureAsync` / `CancelErasureAsync` after `ResolveMyPartyIdAsync()`. The cancel leg applies `CancelPartyErasure` (`Contracts/Commands/CancelPartyErasure.cs:3`), not `EraseParty`. Admin's door is `HttpAdminPortalGdprClient.cs:44` → `EraseParty`.
- **Why it matters:** I7 now makes the door set a closed, ledger-governed enumeration whose changes need an I20 row. An enumeration keyed on names that do not exist cannot be grepped or fitness-tested, and "every path applies the same aggregate command" is falsified by the cancel command on the consumer path. Name the doors by the identifiers that exist (`EraseParty` via `HttpAdminPortalGdprClient`; `ISelfScopedPartiesClient.RequestMyErasureAsync` / `CancelMyErasureAsync` → `EraseParty` / `CancelPartyErasure`), so a future fitness test can pin them.
