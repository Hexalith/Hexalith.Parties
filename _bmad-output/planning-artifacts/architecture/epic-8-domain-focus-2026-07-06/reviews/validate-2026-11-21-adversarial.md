# Epic 8 spine validation · Independent implementation review

**Conditional fail.** Two active rules leave teams with incompatible interpretations of personal-data handling. Two further ambiguities affect rollback evidence and isolated topology qualification. The first three findings from the amendment review are closed. This assessment covers the final spine against Parties revision `42b27f2e` and its committed release selection.

## Findings

1. **High · Erasure takes precedence over last-known display.** I10 and I14 direct the query and UI teams to show last-known data. A UI team could continue showing a previously loaded personal detail when the canonical read fails. The query team already refuses both a populated index and un-erased detail from its local cache when another replica may have erased the party. It preserves a safe empty-index fallback. I7 binds terminal state and I10 excludes erased parties, but neither resolves the case where the consumer cannot establish current erasure state. A user could see inconsistent availability or stale personal information. Amend I10/I14 to require the UI to honor the query outcome, with degraded display restricted to the safe fallback classes the current handlers return. Cite the existing cross-instance tests. 2. **High · Actor-history custody has a separate lifetime.** A crypto migration team implementing I8 could place protected actor-binding history under the party profile key. The attribution team implements an approved policy under which the minimal opaque history has independent custody and may survive profile erasure until 365 fixed days after the original binding-effective time. A shared profile key would make the past attribution record unavailable prematurely. A different implementation could retain a recoverable copy past expiry. I19a assigns ownership of GDPR decisions, but gives no purpose, clock or restore rule for these records. Section 13 describes the design as deferred on October 5. The accepted October 7 policy and completed DW-129 snapshot work supersede that description for current builds. Carry the policy reference into I8 and name its distinct production activation gate. Preserve the historical October record. 3. **Medium · A dependency rollback has two identities.** AD-6 permits a package or gitlink rollback. Section 4 clause 3 requires the reverted tree to be green at the identity stamped by the story’s parity evidence. One team can interpret that as exercising an adapter switch while keeping the new package; another can actually restore the previous package and submit a receipt for that revision. A single undifferentiated stamp cannot describe both runs. I16 establishes how to stamp a result and does not specify which result attests the fallback. Name the forward and rollback configurations separately, keep each receipt attached to the revision exercised, and require the predecessor to read or recover what the forward version wrote where applicable. 4. **Medium · Distinguish canonical and isolated caller identities.** I1 specifies the EventStore-only caller and requires every ACL to retain approved tuples. The canonical declaration renderer also binds the namespace, trust domain and deny defaults. The isolated mTLS AppHost derives a suffixed application ID and matching session namespace. One team could reject this established test profile because its literal caller differs from the canonical one. Another could treat the derived identity as an approved deployment identity. I1a’s eventual handoff approval does not specify how to compare profiles today. Identify the canonical workload identity fields and the existing scoped translation for isolated tests; keep environment-specific deployment changes under I20.
