# OpenBao practical deepening

Accessed 2026-10-25. Publication/update dates not stated in retrieved version-pinned 2.6.x pages. Publisher OpenBao project. Project deployment history is context only; no live cluster was inspected.

Sources:
- O1 https://openbao.org/docs/2.6.x/secrets/transit/ — Transit encrypt/decrypt without storing application payloads, data keys, key version archive and reversible min_decryption_version. Primary docs; medium single-source capability confidence.
- O2 https://openbao.org/docs/2.6.x/api/secret/transit/ — named-key deletion; trim actually removes previous versions from the current keyring; export/plaintext-backup controls; backup and restore of all versions. Primary docs; medium single-source confidence.
- O3 https://openbao.org/docs/2.6.x/api/system/storage/raft/ — restores prior cluster state, including force restore with different seal-consistency validation. Primary docs; medium single-source confidence; backup caveat independently corroborated by prior Azure digest.

How it would work (proposed engineering, not deployed proof): keep EventStore ciphertext and original immutable unit metadata; use dedicated actor-purpose Transit keys per independent erasure unit, or per-unit DEKs with separately destroyable wrapping roots; Platform custody adapter is sole authorized decrypt path and performs original deadline/current authority checks. Direct Transit decrypt keeps data keys inside OpenBao but returns plaintext to application. Application-side envelope encryption instead gives application a DEK, expanding holder scope. Lifecycle cleanup can delete current keys; all prior generations and copies require accounting.

Pros (engineering judgment): reuses existing operator skills/API/auth/audit/restore work; no custom HSM firmware, procurement or enclave attestation; provider can fit existing custody interface; per-unit named keys can isolate normal application deletion. Lowest additional infrastructure only IF existing deployment can be safely owned, separated and sized; generic shared installation is not established custody.

Cons and hard gates: operators still own patching, HA, seal recovery, token/role renewal, backup access and recovery. min_decryption_version is reversible; trim/current deletion is stronger within current state but doesn't erase older backups. Ordinary Raft restore recovers old state; turning off plaintext export/backup does not exclude Raft snapshots. A lifecycle entry restored with that snapshot is not independent authority. Key deletion during outage waits for a worker/service; application plaintext can outlive root destruction. Therefore FAIL as a verified solution to unchanged all-copy exact-deadline/paused-process requirement.

Per-unit trap (inference from O1-O3): one DEK per unit wrapped under a shared persistent master is not independent cryptographic erasure if backed-up wrapped DEKs survive; per-unit context derivation is also reconstructable while the master/context remain. One shared tenant/day key destroys unrelated units or shifts individual deadlines. Separate per-unit key material avoids shared normal-deletion blast radius, but increases key counts and doesn't defeat snapshots.

Conditional pragmatic recommendation: after explicit approval of a different, scoped service-enforcement and bounded-backup-destruction contract, investigate OpenBao first because it is the already-used platform technology. Keep same original365-day exclusive decision boundary, immutable BranchB identity, separate history/profile purpose, fresh authority checks, no persistent plaintext caches/dumps, explicit in-flight/paused-holder limitations, inventory/restore quarantine and honest delayed physical-destruction receipts. Do not select/provision a new backend, change frozen contract, disable required backups or market this as the current guarantee. If the strict original remains mandatory, no OpenBao implementation is recommended.
